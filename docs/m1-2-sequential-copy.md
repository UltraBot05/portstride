# M1.2 sequential copy experiment

The macOS planner and orchestrator are internal. The only construction path for the job executor is in the test fixture code. There is no copy command, public copy API, or authority derived from an M0 inspection report. A job requires the bytes-only metadata acknowledgement and a plan bound to the held source and destination root identities. The planner's conventional name-behavior setting is an explicit fixture assumption, not a filesystem capability measurement.

## Planning and execution

A tree plan maps the contents of one held source root into an existing destination root. A selected-file plan accepts paths beneath one held source root and maps their basenames into the destination root. This permits selections from multiple source subdirectories within the same fixture. It does not authorize arbitrary, unrelated source roots. Plans are bounded to 10,000 items, 64 path components, and 255 bytes per component. Planning holds directory descriptors, rejects a destination inside the source by walking directory identities, checks for mapping collisions, and captures source identities before destination changes.

Names are limited to the transaction's conservative ASCII subset. The planner rejects non-ASCII names because their equivalence is unknown; it does not normalize or rename them. ASCII case-equivalent output mappings and existing entries are conflicts. The executor checks destination names again before directory creation or staging and before each file commit. A concurrent directory writer can change an entry after the last check, so the trusted-directory and no-concurrent-writer assumptions from M1.1 remain necessary.

The executor revalidates the held fixture, manifest, source, destination, and traversed directory identities. It creates new destination directories exclusively with restrictive permissions. It invokes one M1.1 file transaction at a time. The transaction uses exclusive staging, SHA-256 readback, a staging-file sync, and a no-replace commit. The resulting digest describes file bytes, not metadata or a source snapshot. Source and destination directories and their ancestors, ACLs, and mounts must remain trusted throughout the operation. Identity checks detect observed changes but do not prove that no substitution occurred.

Empty directories are created. Symbolic links, including broken links, are reported as unsupported and are not followed. Files with multiple hard links are reported as unsupported; hard-link relationships are not preserved. FIFOs, sockets, devices, and other special objects are reported as unsupported. Unreadable entries or directories fail planning with an error rather than being silently omitted. Directory metadata is not preserved. File copies retain M1.1's bytes-only metadata limitation.

## Outcomes and fixture records

Each planned item has its source and output path and one outcome. Outcomes distinguish a created directory, verified committed file, unsupported item, failure, cancellation, or an item not attempted after a stop. A directory creation with an ambiguous result or an identification failure is reported separately as possibly created. Job summaries count each category and track bytes written and verified. A failed or cancelled job leaves prior committed files in place and never rolls them back or deletes sources. An ambiguous file commit remains in the M1.1 failure result and is not retried automatically.

The manifest records directory and file attempts, identified output directories, stage identities before file I/O, and known successful commits. A manifest failure after a successful commit leaves that file reported as committed, records the observer error, stops the job, and prevents a successful job result. Test fixtures are retained for manual review. They are never cleaned automatically. The fixture setup records identities for created source and destination entries. Regular files and directories are recorded from held descriptors; a symlink is recorded using a no-follow stat because the test does not hold a descriptor for the link itself. The fixture records intentional mutations and substitutions, but it does not implement the complete identity-checked cleanup gate in [m1-fixture-lifecycle-review.md](m1-fixture-lifecycle-review.md). The retained fixtures are not eligible for automatic cleanup.

## Evidence and limits

The focused tests cover empty and nested directories, selected files from separate fixture subdirectories, 200 small files and a file larger than the transaction buffer, binary and empty data, independent system SHA-256 comparison, containment and case conflicts, broken symlinks, hard links, FIFOs, cancellation, source changes, destination replacement, partial failure, and ledger failures. Fault hooks simulate timing-sensitive failures and are not evidence of real disconnect behavior. The test environment denied creation of a Unix socket, so socket handling has not been exercised by an orchestrated socket fixture. Device behavior, mounted filesystem variants, crash recovery, concurrent hostile writers, and power-loss durability remain unverified. No move, deletion, rollback, concurrency, or resume support is included.
