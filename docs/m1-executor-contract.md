# M1.0: single-file copy contract

Status: design for review, not implemented or evidence of copy support. M0's accepted scope is in [m0-acceptance-review.md](m0-acceptance-review.md). The original specifications remain authoritative. This contract applies to M1.1 on macOS; M1.2 and M1.3 are later gates.

## Decisions

1. **Authorization and scope.** `inspect` remains read-only JSON v3 with `transfer_readiness: not_assessed`; neither its report nor exit 0 is a write token. A separate explicit copy request authorizes one regular file to one selected destination directory and final component, subject to fresh validation and the policies below. No moves, source deletion, replacement, resume, background service, or parallelism. M1.1 runs on disposable data until correctness is established.
2. **Conflict.** The only initial policy is `fail_if_exists`. Any existing final entry, including a broken symlink, is a conflict. Check early for useful diagnostics, but only an atomic no-replace commit resolves the race. No rename-overwrite, check-then-rename, or copy-to-final fallback is permitted.
3. **Metadata.** The initial profile copies logical bytes only. It does not promise to preserve mode, ownership, timestamps, ACLs, extended attributes, resource forks, flags, alternate streams, hardlink relationships or sparse allocation. The staging file is created with mode 0600, subject to a more restrictive umask, and that mode persists through rename; other metadata follows filesystem defaults. No chmod broadens access. Before any write the caller must explicitly acknowledge this exact loss profile for this request, even when attributes are absent or unknown. Report the profile and unknowns in the terminal outcome. If the caller requests preservation, or declines acknowledgement, refuse before staging. Metadata read failures must not be interpreted as absence. No silent metadata loss.
4. **Integrity and resources.** Use SHA-256, with an established maintained Rust implementation such as `sha2` subject to dependency review in M1.1. One 1 MiB buffer is the initial fixed upper bound for streaming payload data, reused for staged readback; no size-dependent allocation. Hash bytes read from the source while writing, flush the staged file, then seek and independently read the staged descriptor to EOF and hash it. Require equal digests and byte counts, and source stability checks below. Retry interrupted syscalls and handle short reads/writes; other errors terminate. SHA-256 equality is evidence of byte equality, not metadata equality, a snapshot, or durable media persistence.
5. **Durability.** Require `fsync` on the staging file before verification and treat failure as failure. The selected commit primitive provides no-replace semantics only where supported; no claim is made that a rename, file sync, or directory entry survives power loss. Directory sync and macOS `F_FULLFSYNC` guarantees remain unproven and are not promised. A failure after successful commit cannot be reported as an uncommitted failure.
6. **Paths and platform.** Initially accept only a regular source with link count one, a single final filename component other than `.` or `..`, and existing directories. Reject links, broken links, special files, directories, and hardlinked sources rather than follow or flatten them. Preserve native path bytes in process; never interpolate paths in shell commands. Non-Unix execution fails closed until an adapter provides equivalent guarantees. M1.1 targets macOS and must refuse unsupported filesystem commit semantics, not reject a filesystem solely by name.

## Request and outcome sketch

These are proposed semantic types, not current Rust APIs or a finalized serialization. Use owned native paths at the local Rust boundary. A future external schema must specify a reversible encoding for non-UTF-8 paths before accepting them. Never deserialize an M0 report as this request.

```text
CopyRequestV1 {
  source: PathBuf, destination_directory: PathBuf, final_name: OsString,
  conflict: FailIfExists, metadata: BytesOnlyAcknowledged,
  verification: Sha256Readback, destination_trust: Acknowledged
}
copy(request, cancellation, event_sink) -> CopyOutcome
CopyOutcome = Completed { bytes, digest, metadata_profile, durability }
            | Failed { issue, staging_disposition, commit_state }
            | Cancelled { staging_disposition, commit_state }
```

The request itself is the explicit authority to attempt the write; both the metadata-loss and trusted-destination acknowledgements are required for every API caller, not defaults. Refuse before staging if either is missing. Validate a single normal component without separators, NUL, absolute paths or traversal. Capture fresh source and destination identities in this invocation, not from a previous report. A UI may show a read-only preview, but acceptance of the loss profile and copy must be tied to the actual request and any changed facts require a new decision. A path is not an identity.

Copy-specific structured output, if exposed, uses its own `schema_version: 1` and a distinct `kind`, leaving M0 v3 and its exit codes unchanged. Events have operation ID, sequence number, phase and bytes processed; diagnostic exports redact paths by default. A terminal event is exactly one of `completed`, `failed`, or `cancelled` during normal process execution. Process termination can prevent a terminal event. `completed` requires verified bytes and successful commit. Bytes streamed, bytes verified and commit status are separate; 100% streamed is not completion. Typed issue codes include `INVALID_REQUEST`, `METADATA_ACK_REQUIRED`, `DESTINATION_TRUST_ACK_REQUIRED`, `UNSUPPORTED_TYPE`, `UNSUPPORTED_IDENTITY`, `SOURCE_CHANGED`, `DESTINATION_CHANGED`, `DEST_EXISTS`, `DEST_READ_ONLY`, `DEST_FILE_TOO_LARGE`, `INSUFFICIENT_CAPACITY`, `ACCESS_DENIED`, `IO_ERROR`, `VERIFY_MISMATCH`, `COMMIT_UNSUPPORTED`, and `CLEANUP_FAILED`, with phase, OS cause, confidence and actionable remedy. Represent unknown independently from false. Do not expose untrusted paths in default diagnostics.

## Transaction and identity

The following states are sequential; each transition must succeed before the next. No state is a persistent resume checkpoint.

1. **Validate.** Resolve each source and destination ancestor component relative to an opened trusted root, with no-follow directory opens and identity checks; reject any symlinked ancestor or leaf. Do not rely on M0's `open_directory`, which applies `NOFOLLOW` only to the final component of the path supplied. Classify the source entry without following links before opening; open with no-follow and nonblocking flags so a substituted FIFO cannot block, then immediately validate the opened descriptor. An adapter unable to prevent unsafe device activation or safely classify a raced entry must refuse. Require regular file and link count one, bind its device/inode, size, mtime and ctime to the descriptor, and compare the named entry to it. Bind the destination directory descriptor and volume observations to its device/inode and current mount identity as available. If required identity or a safe resolution is unavailable, refuse. Probe current read-only status, selected-folder access, capacity and known per-file limits against that descriptor. A known insufficient logical capacity is a blocker for this dense-write profile; unknown capacity is reported, and writes can still fail with ENOSPC. FAT-family upper-bound evidence must be qualified; reject sizes above the established upper bound, including FAT32's 4,294,967,295-byte maximum. Unknown limits do not mean unlimited.
2. **Stage.** Create an unpredictable, app-owned name exclusively in the opened destination directory on the destination volume, no-follow, with restrictive creation mode; retain its descriptor and identity. Never open an existing staging entry. No final destination is created here. Validate parent identity and capability observations before write and at commit. Write sequentially through the held descriptor.
3. **Flush and verify.** Finish all writes, sync and read back the same staged descriptor. Compare byte counts and SHA-256. Compare source descriptor identity, type, link count, size, mtime and ctime before and after reading, and recheck the named source entry. Abort on mismatch or inaccessible evidence. These checks detect many changes, but timestamps/identity are not a snapshot and cannot exclude every concurrent same-size mutation or adversarial restoration. The digest describes the stream actually read, not necessarily one instantaneous source version. If stronger snapshot semantics are required, refuse until provided.
4. **Commit.** Recheck the destination chain, mount and held directory identity, source consistency, and staging name-to-descriptor identity immediately before commit. Use `renameatx_np` with both directory descriptors and `RENAME_EXCL` on macOS. The local `rename(2)` manual specifies `EEXIST` for an existing target and `ENOTSUP` when the filesystem does not support the flag; it describes exclusive behavior on supporting filesystems. Test actual behavior on each target filesystem before claiming atomicity. Treat unsupported or ambiguous errors as failure; no unsafe fallback. Success is the commit linearization point. Report completion only after success. If the system call outcome is ambiguous, report `commit_state: unknown`, do not retry blindly or claim no final file exists, and require inspection.
5. **Failure or cancellation.** Poll cancellation before staging, between I/O operations, before verification and immediately before commit. Once the commit syscall begins, resolve its result before reporting: successful commit wins over a concurrent cancellation. Never delete a committed destination or source. Before commit, cleanup is best effort only for the exclusively created staging entry if its name still identifies the held file in the held directory; otherwise leave it and report the disposition. A check followed by unlink is not atomic against a hostile directory writer: only attempt cleanup under the trusted-directory assumption below. If cleanup fails or ownership cannot be proved, report the residue, redacted by default. Crash or disconnect can leave staging files; no automatic scan, cleanup or resume in M1. Never present them as completed files.

## Threat model and limits

Descriptor-relative no-follow traversal prevents substitution from redirecting a subsequent open through a symlink; descriptor binding means a renamed open directory remains the same object. Revalidation catches observable replacement, but it is not atomic with commit. A writable ancestor can be renamed between the last check and commit, so the destination can move and the selected path can cease to name it. Name-based staging commit and cleanup can race a writer with permission to change that directory. M1.1 therefore requires a trusted destination directory and ancestor chain, including ACLs, with no concurrent actor able to rename or replace entries or mounts during the operation. Mode bits alone do not establish this; the caller must explicitly ensure the assumption, and the contract must disclose it. The source path and ancestors also require no concurrent actor able to substitute entries during classification and open; a nonblocking flag alone does not make opening a device safe. An adversarial same-user process, privileged actor, hostile server, mount replacement, inode reuse, and concurrent source writer are outside the guarantee. Refuse when required conditions or safe operations cannot be established; never advertise complete protection against malicious concurrent writers. Detect observed changes and fail closed. Destination no-clobber still protects an existing final entry against the commit race when the primitive actually provides its documented semantics.

Capacity, writability, mount IDs and capability probes are point-in-time observations, not reservations or proof of future behavior. An opened descriptor can outlive a path rename, disconnect or remount. Network and NTFS write semantics are unverified; unknown capability is not a blanket filesystem denial, but missing required no-clobber or identity guarantees blocks execution. No tests of real copy, crash durability or metadata preservation are claimed by M0.

## Required test matrix and phase gates

All M1.1 tests use disposable directories or injected adapters, never real user files. Tests assert source and pre-existing destination bytes unchanged, no false completion, and explicit staging disposition on every failure. Label simulated faults separately from real filesystem evidence.

| Scenario | Required result |
| --- | --- |
| Empty, normal, large and sparse logical source | Independent SHA-256 and byte counts match; sparse allocation is not claimed; bounded buffer. |
| Known FAT32 limit and insufficient capacity | Reject > 4,294,967,295 bytes and known inadequate capacity before staging; test boundary and unknown evidence separately with mocks. |
| Existing file, directory, symlink, broken symlink, or final appears at commit | Conflict; no replacement. Test concurrent commit race against actual primitive. |
| Source leaf or ancestor symlink, broken link, FIFO, device, directory, hardlink | Explicit rejection before staging; FIFO substitution cannot block, device substitution cannot activate a device, and non-Unix adapter refuses. |
| Source renamed, replaced, truncated or modified during read | Observed identity/metadata change fails; include same-size changes and state the limits of detection. |
| Destination ancestor or mount changed, stage name swapped | Abort when observed; demonstrate trusted-directory boundary and no write through a substituted symlink. Test pre-commit race limitations explicitly. |
| Short read/write, EINTR, read/write/seek/sync failures, ENOSPC, disconnect, digest mismatch | Correct retry only for interruption; otherwise fail without final completion; report cleanup and errors. |
| Cancel before stage, during stream/readback, immediately before and during commit | No false completed result; successful commit wins; residual stage is reported. |
| Missing metadata or destination-trust acknowledgement, unsupported requested metadata, metadata read error | Refuse before writing or explicitly report unknown under accepted bytes-only profile; never claim preservation. |
| Crash before/after commit, cleanup failure, unsupported commit | No blind resume or destructive cleanup; outcome reflects known or unknown commit state. |
| M0 compatibility | Existing v3 fixtures, redaction and inspect exits remain unchanged. |

M1.1: implement and test the single-file core, fresh validation, restrictive staging, digest readback, no-clobber adapter, cancellation, reporting and negative cases above. Run formatting, Clippy, workspace tests, docs and disposable CLI hash smoke tests; obtain independent security review and fix major findings. The contract is a design, not proof that a safe implementation is possible under every filesystem.

M1.2: only after M1.1 acceptance, compose sequential single-file transactions for trees, detect destination-inside-source and mapping/case/Unicode collisions, define empty directory and symlink policies, and report per-item committed and failed outcomes. A tree is not atomic; earlier committed files remain on later failure.

M1.3: only after M1.2 acceptance and separate explicit approval for image lifecycle and fixture writes, test fresh manifest-owned disposable APFS case variants, exFAT and FAT32. Verify hashes, no-clobber, the real FAT32 size guard without writing an oversized file, cancellation, naming and metadata outcomes. Benchmark verified sequential copies against system tools with equivalent metadata and verification semantics and recorded cache conditions. Do not infer copy support from M0's read-only image observations.

## Open decisions

- Exact API/CLI spelling, event serialization, error mapping and approved SHA-256 dependency version are M1.1 implementation choices subject to review; no new schema exists yet.
- How the caller establishes the trusted-directory/no-concurrent-writer assumption, and whether a stronger platform mechanism can reduce it, must be resolved before enabling any copy execution; acknowledgement alone does not prove it. If the assumption is unacceptable, keep execution disabled rather than claim a guarantee the OS interfaces do not provide.
- Actual `RENAME_EXCL` support and atomicity on each mounted filesystem, directory sync behavior, stronger power-loss guarantees, source snapshots and metadata preservation require evidence. No fallback has been approved.
- A stronger move verification policy, source deletion, replacement, resumable journal, Windows execution and concurrency are outside M1.0 and need their own decisions and authorization.
