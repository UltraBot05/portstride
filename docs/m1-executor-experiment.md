# M1.1 disposable copy experiment

Status: M1.1 accepted for controlled single-file copying under the trusted-directory assumptions below. The macOS transaction and its descriptor-based authorization provider compile in the platform library. The provider is internal to the crate; there is no copy command or public executor. The M1.0 contract and original specifications remain the design baseline.

The tests create a randomly named directory below the process temporary directory, open it through descriptor-relative operations, and create their own source file. Copying uses a separate bytes-only acknowledgement, an exclusive 0600 staging file, a bounded buffer, SHA-256 staging readback, a staging-file sync, and macOS exclusive rename. Final permissions are the creation mode restricted by the process umask; metadata preservation and power-loss durability are not promised. Tests compare source and destination bytes and use the system `shasum` command for an independent digest check.

New fixtures create a private manifest containing newline-delimited JSON records, despite its `.json` suffix. It records the held parent, root, manifest and source identities; a normal copy records its staging identity before I/O and a known successful rename afterward. An explicit cleanup can remove an untouched fixture or a recorded successful copy only after checking the complete entry set and each held identity without following links. Failed or ambiguous copies, unregistered mutations, identity changes, unexpected entries and incomplete ledger updates remain ineligible and are left for manual review. There is no recursive cleanup or automatic crash recovery. A process termination can prevent any outcome from being reported.

The experiment assumes both source and destination directories and their ancestors, including ACLs, are trusted and that no actor substitutes entries, directories or mounts during setup or execution. It also assumes a non-hostile filesystem with conventional name equivalence. Owner and mode checks do not prove those assumptions. Another actor could replace a newly created directory before its first identity observation. The destination recheck does not establish a stable mount identity or close the race between checking a name and rename or unlink. Source timestamp and identity checks do not provide a snapshot or detect every concurrent mutation. Rust visibility does not isolate the capability from hostile code in the same process.

The transaction and fixture harness are separate modules in `platform-macos/src/`. The transaction and authorization provider compile outside tests. The provider binds the selected source descriptor to a no-follow source entry, checks the destination descriptor against its parent entry and probe, requires bytes-only acknowledgement, and rejects existing final entries. Source and destination can use separate held directories. The executor rechecks identities before staging and commit and consumes the request. These checks detect observed replacement; they do not establish user intent or the trusted-directory assumptions. A future native interface must establish intent and supply the selected resources. The caller supplies a fresh unpredictable staging name.

The probe gives point-in-time capacity, access, and filesystem limit observations. A device identifier is not proof of mount identity. Unknown observations do not establish support. Exclusive rename is tested on the filesystem hosting the temporary directory, not across the supported filesystem matrix. A rename error other than the known conflict or unsupported cases leaves the commit state unknown and avoids cleanup.

Tests cover fixture copies, conflicts, source type rejection including a FIFO, cancellation at selected points, observed source and destination changes, stage substitution, and injected phase failures. The workspace regression suite passed 114 tests, including the focused unknown-access test. Fixtures with uncertain or intentional mutations remain preserved. Short reads and writes and interrupted I/O are exercised with in-memory test implementations. Injected phase failures are not kernel-level sync, seek, commit, disconnect, or cleanup failures. Test-only injections simulate an unknown commit result both before rename and after a successful real rename; these verify that an unknown outcome does not trigger staging cleanup, but do not reproduce an ambiguous syscall result. Actual ambiguous syscall outcomes remain unverified. Failure outcomes expose written, read-back and verified byte counts, sync status, commit state, and cleanup errors. Final names are restricted to ASCII alphanumeric characters initially, followed by ASCII alphanumerics, dots, underscores or hyphens. Staging names start with `.portstride-` followed by 32 lowercase hexadecimal characters. These disjoint patterns prevent ordinary case or Unicode folding from equating the names under the stated filesystem assumption. General filename support and arbitrary filesystem equivalence remain unresolved. Event serialization is not implemented.

## Boundary defect during development

A development test passed a traversal component to the transaction before component validation existed. The exclusive rename created a new six-byte fixture file in the temporary parent, outside the intended fixture directory. The transaction did not overwrite an existing entry. The file was left in place because the transaction had already committed it and the staging identity was not recorded at commit. The user-facing completion report must identify its location. The provider now validates filename components before filesystem operations. Separate component validation tests reject separators, NUL, empty names, and dot components. A transaction-level regression also attempts traversal and absolute output names against a separate disposable fixture and checks that its sentinel remains unchanged. This incident means the experiment did not maintain the requested boundary throughout development.

A separate disposable test showed that macOS can report success when exclusive rename names the same entry as both source and destination. The provider restricts the stage and final names to distinct patterns before staging. General filename alias handling remains unresolved.

## Read-only incident inspection

A read-only inspection observed the previously reported escaped entry as a regular file. A no-follow open followed by descriptor identity comparison read the bytes `source`. Its observed identity matched the earlier observation, but the original transaction did not record its committed identity, so this is not independent proof of ownership. Reading can update access time. The defect was an unchecked `../escape` final component passed to descriptor-relative exclusive rename before the later request validation was added.

A read-only, no-follow inventory of the temporary parent found 392 directory entries matching the fixture naming pattern and 44 entries with staging-name prefixes inside them. Names alone do not establish provenance or ownership. No artifacts were removed. Before any cleanup, obtain explicit approval, independently establish ownership of each object, revalidate identities at removal and use an appropriately confined procedure. Do not recursively delete a path merely because its name matches the fixture pattern.
